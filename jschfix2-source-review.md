## OBSERVED

- In `Channel`, `setOpenConfirmation`, the open wait loop, the final open decision, and `close` now use the Channel monitor. The final decision sets `connected` only after confirming that the stream is not closed, has a peer recipient, and received an open confirmation. `close` marks the stream closed and notifies waiters. See [Channel.java:160](/home/u/lanes/util20261014/workspace/jschfix2/src/main/java/com/jcraft/jsch/Channel.java:160), [Channel.java:629](/home/u/lanes/util20261014/workspace/jschfix2/src/main/java/com/jcraft/jsch/Channel.java:629), and [Channel.java:875](/home/u/lanes/util20261014/workspace/jschfix2/src/main/java/com/jcraft/jsch/Channel.java:875).
- `disconnect()` now calls `close()` even when `connected` is false, then removes the local Channel from the pool in its `finally` path. This marks a pending open as terminal and wakes the open caller. See [Channel.java:684](/home/u/lanes/util20261014/workspace/jschfix2/src/main/java/com/jcraft/jsch/Channel.java:684).
- When the Session reader receives an open confirmation, it publishes the peer recipient only if the Channel is still open. If lookup fails or the Channel has already closed, it sends `SSH_MSG_CHANNEL_CLOSE` to the peer recipient carried by that confirmation. See [Session.java:1926](/home/u/lanes/util20261014/workspace/jschfix2/src/main/java/com/jcraft/jsch/Session.java:1926).
- The `Channel` buffer, read, and receive-credit writer methods are unchanged by this patch. The Session packet writer is unchanged too; the Session diff is limited to open-confirmation handling.
- `ChannelDirectTCPIP` is the only `Channel` subclass that overrides `connect(int)`. Both its synchronous path and its worker-thread path still call the shared `sendChannelOpen()`. A timeout closes the base Channel before throwing; the synchronous handler closes its IO and removes the Channel, while the worker handler disconnects it. `ChannelDirectStreamLocal` inherits this behavior. See [ChannelDirectTCPIP.java:57](/home/u/lanes/util20261014/workspace/jschfix2/src/main/java/com/jcraft/jsch/ChannelDirectTCPIP.java:57) and [ChannelDirectTCPIP.java:83](/home/u/lanes/util20261014/workspace/jschfix2/src/main/java/com/jcraft/jsch/ChannelDirectTCPIP.java:83).
- `ChannelSession` subclasses, including exec, shell, SFTP, and subsystem channels, use the base `connect(int)`. Forwarded, X11, and agent channels are peer-accepted paths and do not call `sendChannelOpen()` themselves. The SFTP disconnect override delegates to the base implementation.
- The added test assertions now check that pending disconnect leaves the local Channel closed and disconnected, and that no command starts after the delayed reply. The README describes timeout, pending-disconnect, and no-reply behavior consistently with the implementation.
- The master-based commit applies the same lifecycle logic to its own base revision. Its source changes do not add a separate `ChannelDirectTCPIP` change.

## INFER

- The main state transition is serialized correctly. If the reply handler gets the Channel monitor first, it publishes the peer recipient and the waiting caller can complete normally. If timeout or local disconnect gets the monitor first, it marks the Channel closed; the waiter sees that state even if it starts waiting afterward, and a reply handler that already has a Channel reference rejects the reply. If pool lookup happens after removal, the handler still sends CLOSE from the reply's peer recipient. This covers pending disconnect both before and after the caller parks, without a separate pending-open map.
- The session-close control remains valid. Before any open confirmation, the client has no peer recipient to address, so local channel close sends no packet; `Session.disconnect()` then closes the transport, which owns cleanup for peer streams whose open reply never arrived.
- A normal acknowledgement still carries window size, packet size, open status, and peer recipient before notifying the opener. The caller sets `connected` under that same monitor, so the new terminal check does not turn a normal open into a failure. Connected sibling channels continue using the unchanged output and receive-credit paths.
- `ChannelDirectTCPIP` and its stream-local subclass use the same terminal state and reply handling. I found no regression in their normal open, timeout, or local-disconnect paths.
- I found no concrete blocker in the pushed source change. These are source-level conclusions only; the targeted runs were not executed as part of this review.
